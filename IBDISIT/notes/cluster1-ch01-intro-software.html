1.1 Software Fundamentals, Failure Curves, Domains & Lehman's Laws

Conceptual Core

According to the IEEE Standard Glossary of Software Engineering Terminology, software is NOT merely executable code—it comprises three inseparable components: (1) Instructions (Computer Programs) that provide desired features, function, and performance when executed; (2) Data Structures that enable programs to manipulate information; and (3) Descriptive Information (Documentation & Configuration) in both hard-copy and virtual forms describing operation and use.

A. Hardware Bathtub Curve vs. Software Deterioration Curve

A classic regulatory IT exam distinction: physical hardware wears out due to dust, vibration, thermal stress, and component fatigue, following the Bathtub Curve (high infant mortality → flat useful life → steep wear-out phase). Software is immune to physical wear-out; theoretically its failure curve should flatten after initial debugging (Idealized Curve). In reality, continuous feature additions and patches introduce side effects / regression defects, causing failure-rate spikes after every release—a phenomenon called Software Deterioration (Software Rot).

B. Pressman's 7 Software Application Domains

Domain Defining Characteristics Real-World & Banking Examples
1. System Software Services other programs; heavy hardware interaction, concurrency, resource scheduling. Linux Kernel, z/OS, Device Drivers, Compilers, File Systems.
2. Application Software Standalone programs solving a specific business need (real-time or batch). Core Banking (Finacle/Flexcube), Tally, Point-of-Sale (POS), Payroll.
3. Engineering / Scientific "Number-crunching" algorithms, CAD, simulation, matrix/Monte Carlo models. Quantitative risk Monte Carlo engines, MATLAB, weather modeling.
4. Embedded Software Resides in ROM/Flash inside hardware products; strict real-time & memory limits. ATM controller firmware, POS EMV card reader chip OS, HSM microcode, IoT sensors.
5. Product-Line Software Mass-market tools targeting diverse consumers with shared core capabilities. MS Office, Adobe Suite, database management tools, inventory packages.
6. Web & Mobile Apps (WebApps) Network-centric, continuous evolution, multi-tenant browser/mobile delivery. SIDBI Udyamimitra, GST Sahay mobile app, UPI/NetBanking portals.
7. AI Software Non-numerical algorithms solving complex heuristic/pattern problems. Credit-default ML classifiers, AML transaction-monitoring AI, LLM chatbots.

C. Legacy Software & Lehman's Laws of Software Evolution

Legacy Software refers to mission-critical older systems (often written decades ago in COBOL, RPG, or early Java) that remain vital to business operations but exhibit brittle architectures, poor documentation, and high maintenance cost. Meir Lehman formulated 8 Laws of Software Evolution for E-type (real-world embedded) systems—4 are most tested:

  • Law 1 — Continuing Change: An E-type system must be continually adapted or it becomes progressively less satisfactory.
  • Law 2 — Increasing Complexity: As a system evolves, its complexity increases unless explicit work (refactoring) is done to maintain or reduce it.
  • Law 6 — Continuing Growth: Functional content must continually increase to maintain user satisfaction over its lifetime.
  • Law 7 — Declining Quality: Perceived quality will decline unless rigorously maintained and adapted to operational environment changes.

1.2 System Software, Firmware, Boot Pipeline & Enterprise Middleware

High Objective & Banking Yield

A. Complete Cold-Boot Sequence & Legacy BIOS vs. UEFI

Boot Pipeline: Power-On → CPU Reset Vector → Firmware POST (Power-On Self-Test) → Boot Device Discovery → Bootloader (GRUB2 / Windows Boot Manager) → OS Kernel Load & Init (systemd / PID 1) → User-Space Services & Login.

Parameter Legacy BIOS (Basic Input/Output System) UEFI (Unified Extensible Firmware Interface)
Processor Mode 16-bit Real Mode (1 MB addressable space during boot) 32-bit or 64-bit Protected/Long Mode
Partition Table MBR (Master Boot Record) — max 4 primary partitions GPT (GUID Partition Table) — up to 128 partitions (Windows default)
Max Boot Disk Size 2.2 TB (32-bit sector addressing) 9.4 Zettabytes (ZB) (64-bit LBA)
Security No cryptographic verification; vulnerable to MBR bootkits Secure Boot verifies digital signatures of bootloader/kernel (PK, KEK, db, dbx)
Interface & Speed Text-only, keyboard-driven, sequential hardware init GUI + mouse + networking support; parallel driver init (faster boot)

B. Device Drivers & Utility Software

  • Device Drivers: Hardware-specific translators allowing the OS kernel to communicate with peripherals via standardized I/O interfaces without knowing hardware register internals. Categorized into Character drivers (byte streams: keyboard, serial), Block drivers (fixed blocks with random access: SSD, HDD), and Network drivers (packet frames: NIC).
  • Kernel-Mode vs. User-Mode Drivers: Kernel-mode drivers run in Ring 0 (fastest, but a bug causes BSOD / Kernel Panic); User-mode drivers run in Ring 3 (safer isolation, slight context-switch overhead).
  • Utility Software: Always classified as a subset of System Software—includes antivirus/EDR, backup/snapshot agents, disk defragmenters, compression tools (gzip/tar/7z), and system monitors.

C. Enterprise Middleware Taxonomy (Banking Integration Backbone)

Middleware Type Communication Pattern Key Examples Banking / SIDBI Use Case
MOM (Message-Oriented Middleware) Asynchronous queues & pub/sub topics (decoupled, guaranteed delivery) IBM MQ, Apache Kafka, RabbitMQ Queuing NEFT/RTGS/UPI alerts, fraud-event streaming, loan status sync.

1.3 Language Generations, Translators, Compilers, Linkers & Loaders

Top Paper III Objective Zone

A. Five Generations of Programming Languages (1GL – 5GL)

Gen Category Abstraction & Portability Examples
1GL Machine Language Pure binary (0s & 1s); hardware-dependent; no translator needed; fastest execution. x86 / ARM binary opcodes
2GL Assembly Language Mnemonics (MOV, ADD, JMP); hardware-dependent; requires an Assembler. x86-64 NASM, ARM Assembly
3GL High-Level Procedural / OOP Machine-independent; English-like syntax; requires Compiler or Interpreter. C, C++, Java, Python, COBOL, Go
4GL Declarative / Non-Procedural Specifies "WHAT" to compute, not "HOW"; built for databases, reporting & analytics. SQL, SAS, MATLAB, ABAP, R
5GL Logic / Constraint / AI Solver-driven: define constraints/facts/rules; system deduces solution. Prolog, OPS5, Mercury

B. End-to-End C Compilation Toolchain (Exact File Extensions)

/* Step-by-step GCC build pipeline (frequently asked in Paper III MCQs) */
main.c  --[Preprocessor: #include, #define, strip comments]-->  main.i (Expanded C source)
main.i  --[Compiler: 6 phases, optimization]----------------->  main.s (Assembly code)
main.s  --[Assembler: mnemonics to binary opcodes]----------->  main.o (Relocatable Object file)
main.o + libc.a/libc.so --[Linker: symbol resolution]-------->  a.out  (Executable ELF/PE binary)
a.out   --[OS Loader: map segments into RAM, set PC]--------->  Running Process in Memory

C. Compiler vs. Interpreter vs. Hybrid JIT (JVM / CPython / V8)

Dimension Compiler (AOT) Pure Interpreter Hybrid + JIT (Java, C#, JS V8)
Translation Unit Translates entire source file into target machine code beforehand. Reads, parses, and executes one statement/line at a time. Compiles source → platform-independent Bytecode; VM interprets + JIT-compiles hot loops.
Runtime Speed Fastest (direct native CPU execution). Slowest (re-translates every iteration of a loop). Near-native after warm-up via profile-guided JIT optimization.
Portability Low binary portability (must recompile per OS/CPU ISA). High (runs anywhere interpreter exists). Write Once, Run Anywhere (WORA) via JVM/CLR abstraction.
Error Detection Reports all compile-time syntax & type errors together. Halts immediately at the first offending statement at runtime. Syntax/static-type errors caught at bytecode compile time; runtime exceptions in VM.
Special Variants • Cross-Compiler: Runs on Host architecture (e.g., x86 PC) to emit machine code for a different Target (e.g., ARM IoT chip).
• Transpiler (Source-to-Source): Translates one HLL to another HLL (e.g., TypeScript → JavaScript via tsc/Babel).
• Bootstrapping: Writing a compiler for language L in language L itself (represented via T-Diagrams).

D. Six Phases of a Compiler (Analysis Front-End vs. Synthesis Back-End)

Phase Stage Input → Output Formal Theory / Core Task (Exam Gold)
1. Lexical Analysis (Scanner) Front-End (Analysis) Char stream → Tokens Uses Regular Expressions & Finite Automata (DFA/NFA). Removes whitespace/comments; inserts identifiers into Symbol Table.
2. Syntax Analysis (Parser) Front-End (Analysis) Tokens → Parse Tree / AST Uses Context-Free Grammar (CFG) & Pushdown Automata (PDA). Top-Down (LL(1), Recursive Descent) & Bottom-Up (LR, LALR, SLR).
3. Semantic Analysis Front-End (Analysis) AST → Annotated AST Type checking, implicit type coercion, scope resolution, array-bound/undeclared variable checks using Attribute Grammars.
4. Intermediate Code Gen Middle (IR) Annotated AST → IR Produces machine-independent Three-Address Code (TAC), Quadruples, Triples, or SSA (Static Single Assignment, used in LLVM).
5. Code Optimization Middle IR → Optimized IR Constant folding (2+3 → 5), dead-code elimination, common subexpression elimination, loop-invariant code motion, strength reduction (x*2 → x<<1).
6. Target Code Generation Back-End (Synthesis) Optimized IR → Machine Code Register allocation (NP-complete, solved via Graph Coloring), instruction selection, instruction scheduling, peephole optimization.

E. Linkers & Loaders — Complete Comparison

Component / Scheme Core Mechanism Pros & Exam Traps
Static Linker Copies library object code (.a / .lib) directly into executable before run time. Self-contained binary, no "DLL Hell", slightly faster call speed; larger disk/RAM footprint; must recompile to patch library CVEs.
Dynamic Linker Stores only stub references; links shared libraries (.so on Linux, .dll on Windows) at load-time or run-time (dlopen). One copy of library shared in RAM across all processes; instant security patching; requires Position-Independent Code (PIC) & GOT/PLT tables.
Absolute Loader Loads machine code into fixed hardcoded memory addresses specified by assembler. Simplest & fastest loader, but no relocation or multiprogramming flexibility.
Relocating Loader Adjusts address-sensitive instructions at load time using a Relocation Table / Bitmask so program can load at any free RAM address. Essential for multiprogramming OS where load address is unknown at compile time.
Bootstrap Loader Tiny ROM/UEFI loader that loads the OS kernel from disk into RAM at startup. First software component to transfer control from firmware to OS.

1.4 Virtualization, Containers & Cloud Software Delivery Models

Modern Enterprise IT

Modern banking and SIDBI IT infrastructure rarely deploys one application per physical server. Software runs on layered abstraction platforms:

Dimension Type-1 Hypervisor (Bare-Metal) Type-2 Hypervisor (Hosted) Containers (Docker / OCI / K8s)
Runs Directly On Physical Hardware (no host OS) Host Operating System (Windows/Linux) Host OS Kernel via Linux Namespaces & cgroups
Guest OS Full Guest OS per VM (heavy: GBs) Full Guest OS per VM Shares Host OS Kernel (lightweight: MBs)
Startup & Density Minutes; tens of VMs per server Minutes; lower performance (host OS overhead) Milliseconds–seconds; hundreds per server
Isolation Strength Hardware-level strong isolation (best for multi-tenant banking cores) Good (used for dev/test laptops) Process-level isolation (kernel CVE affects all containers on host)
Examples VMware ESXi, Linux KVM, Microsoft Hyper-V, Xen Oracle VirtualBox, VMware Workstation Docker, containerd, Podman, Kubernetes

Cloud Service Models (Shared Responsibility Boundary)

  • IaaS (Infrastructure as a Service): Provider manages physical DC, networking, storage, servers & virtualization; Customer manages OS, middleware, runtime, app & data (e.g., AWS EC2, Azure VMs).
  • PaaS (Platform as a Service): Provider also manages OS, patching & runtime; Customer manages only Application Code & Data (e.g., Azure App Service, Google App Engine, RDS).
  • SaaS (Software as a Service): Provider manages full stack; Customer manages only user access, configuration & data governance (e.g., Microsoft 365, Salesforce, Zoho).
  • FaaS (Function as a Service / Serverless): Event-driven, auto-scaling stateless functions billed per millisecond of execution (e.g., AWS Lambda).

1.5 Software Licensing, FOSS Governance & Supply-Chain Security (SBOM)

High Exam Trap Zone
License Category Source Access Commercial Use & Closed Derivatives? Key Legal Clauses & Examples
Proprietary / Commercial Closed Restricted by EULA (per-seat / per-core / enterprise) Oracle DB, MS Windows Server, Finacle CBS. Vendor holds all IP.
Freeware Closed Free of cost (gratis), but no right to inspect/modify source Adobe Acrobat Reader, Skype. Trap: Freeware ≠ Free Software (FOSS).
Shareware Closed Time-limited or feature-limited trial ("try before buy") WinRAR, trial security utilities.
Permissive FOSS Open YES — closed-source commercial derivatives allowed MIT, BSD (2/3-Clause), Apache 2.0 (Apache 2.0 adds explicit patent grant & retaliation clause).
Weak Copyleft FOSS Open Closed apps may dynamically link; edits to library stay open GNU LGPL (library-level), MPL 2.0 (file-level copyleft).
Strong Copyleft FOSS Open NO — "Viral" clause forces entire derivative under same license GPLv2 (Linux kernel), GPLv3 (adds anti-Tivoization + patent grant), AGPLv3 (triggers even over SaaS/network use without binary distribution).
Public Domain / CC0 Open Unrestricted; copyright waived or expired SQLite, CC0 works.
2025–2026 Enterprise Software Supply-Chain Essentials • SBOM (Software Bill of Materials): A formal machine-readable inventory (in SPDX or CycloneDX format) listing every open-source & third-party dependency inside a software build—critical for rapid incident response during zero-day supply-chain flaws (like Log4Shell).
• Software Escrow: A tripartite agreement where a vendor deposits critical source code and build scripts with a neutral escrow agent, released to the bank/AIFI if the vendor goes bankrupt or breaches SLA.

  • Product Operation (using it): Correctness, Reliability, Efficiency, Integrity, Usability.
  • Product Revision (changing it): Maintainability, Flexibility, Testability.
  • Product Transition (moving it): Portability, Reusability, Interoperability.

C. Software Crisis, Brooks' Law & Conway's Law (With Worked Numerical)

  • Software Crisis (coined at 1968 NATO Software Engineering Conference): Chronic schedule overruns, budget overruns, low quality, and unmaintainable code as hardware power outpaced ad-hoc coding practices.
  • Brooks' Law (The Mythical Man-Month): "Adding manpower to a late software project makes it later" due to ramp-up time and quadratic communication channels: C = n(n - 1) / 2.
  • Conway's Law: Organizations design software architectures that mirror their own internal communication structures (e.g., 4 siloed departments produce a 4-pass compiler or 4 tightly coupled monoliths).
Worked Numerical — Brooks' Law Communication Overhead Question: A banking software team of 6 engineers is expanded to 12 engineers to recover a delayed release. Calculate the percentage increase in pairwise communication channels.
Step 1: Initial channels (n = 6): 6 × 5 / 2 = 15 channels.
Step 2: Expanded channels (n = 12): 12 × 11 / 2 = 66 channels.
Step 3: Increase = 66 - 15 = 51 channels → Percentage increase = (51 / 15) × 100 = 340% increase (doubling headcount more than quadruples coordination channels!).

1.8 5-Minute Rapid Revision Sheet (20 High-Yield One-Liners)

Last-Day Cram
  1. Software = Programs + Data Structures + Documentation (IEEE); engineered, not manufactured.
  2. Hardware follows the Bathtub Curve; Software suffers deterioration spikes after changes (no physical wear-out).
  3. Lehman's Law 2: System complexity increases over time unless explicit refactoring is performed.
  4. UEFI replaces 16-bit BIOS with 32/64-bit mode, GPT (>2.2 TB, up to 9.4 ZB), and cryptographic Secure Boot.
  5. Utility Software (AV, backup, compression) is a subset of System Software, not Application Software.
  6. Kernel-mode drivers run in Ring 0 (fast, crash = Kernel Panic/BSOD); User-mode drivers run in Ring 3.
  7. MOM (Kafka/IBM MQ) = asynchronous decoupled messaging; TP Monitor (CICS) = distributed ACID (2PC).
  8. 4GL (SQL, SAS) = declarative ("what", not "how"); 5GL (Prolog) = logic/constraint-based AI.
  9. C Build Pipeline: .c → .i (Preprocessor) → .s (Compiler) → .o (Assembler) → Executable (Linker) → RAM (Loader).
  10. Compiler Front-End = Lexical (Regex/DFA) + Syntax (CFG/PDA) + Semantic (Type/Scope).
  11. Register Allocation in Back-End Code Generation is solved via Graph Coloring.
  12. Cross-Compiler compiles on Host ISA for a different Target ISA; Transpiler translates HLL → HLL.
  13. Dynamic Linking (.so/.dll) shares one library in RAM across processes and enables patching without recompiling.
  14. Relocating Loader adjusts addresses at load time for multiprogramming; Absolute Loader uses fixed addresses.
  15. Type-1 Hypervisor (ESXi/KVM) runs on bare metal; Containers share host OS kernel via namespaces & cgroups.
  16. Freeware = gratis but closed-source (NOT FOSS); Apache 2.0 = permissive + explicit patent grant.
  17. AGPLv3 closes the SaaS loophole—triggers copyleft disclosure even over network interaction.
  18. SBOM standard formats: SPDX and CycloneDX.
  19. ISO/IEC 25010 = 8 characteristics (F-P-C-U-R-S-M-P); Brooks' Law channels = n(n-1)/2.
  20. RBI AIFI IT Outsourcing Directions: Compliance deadline April 10, 2026; mandatory exit plan & data sanitization.
