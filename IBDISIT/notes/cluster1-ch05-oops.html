5.1 OOP Paradigm, The Four Pillars & Access Specifiers

Core Foundation

Object-Oriented Systems organize software around Objects—runtime instances of a Class (blueprint) combining State (attributes/fields), Behavior (methods), and Identity (unique memory/object reference). Unlike procedural programming (functions operating on exposed global data), OOP binds data and operations together to maximize modularity and maintainability.

OOP Pillar Core Definition Mechanism Classic Exam Trap / Distinction
1. Encapsulation Bundling data + methods into one unit and restricting direct access to internal state. private fields + validated getters/setters Implementation-level ("HOW" data is protected from invalid mutation).
2. Abstraction Exposing only essential external behavior while hiding complex internal details. Abstract classes, Interfaces, API contracts Design-level ("WHAT" an object does; e.g., disburseLoan() hides ledger/SMS/audit internals).
3. Inheritance Deriving a specialized subclass (IS-A) from a base superclass to reuse and extend behavior. extends (Java), : public (C++), class B(A) (Python) Overusing deep inheritance creates Fragile Base Class tight coupling → prefer Composition!
4. Polymorphism "Many forms" — one interface/call invokes different behaviors depending on type. Static: Overloading, Templates
Dynamic: Overriding (virtual)		 Early (Compile-time) binding = Overloading; Late (Runtime) binding = Overriding.

5.2 Class Relationships: Association, Aggregation, Composition & UML Notation

Top Paper III MCQ Trap
Exam Trap: Aggregation vs. Composition Lifecycle Test Ask: "If the Whole (Parent) object is deleted, do the Part (Child) objects cease to exist?"
• NO (employees still exist if a bank branch closes) → Aggregation (Hollow Diamond).
• YES (an invoice's line-items or a loan's EMI schedule cannot exist independently without the parent loan) → Composition (Filled Black Diamond).
• Dependency (dashed open arrow - - ->) is the weakest relationship: Class A temporarily uses Class B as a method parameter or local variable.

5.3 SOLID Design Principles, Cohesion/Coupling & Law of Demeter

High Objective & Descriptive Yield
Principle Exact Definition (Robert C. Martin) Banking Violation vs. Clean Refactor
S — Single Responsibility (SRP) A class should have only ONE reason to change. Bad: Loan class calculates EMI, writes SQL, and sends SMS.
Good: Split into EMICalculator, LoanRepository, NotificationService.
O — Open / Closed (OCP) Open for extension, closed for modification. Bad: Adding a new MSME scheme requires editing a giant if-else block.
Good: Implement a new SchemeRule class behind a common interface.
L — Liskov Substitution (LSP) Subtypes must be substitutable for their base types without breaking correctness. Classic Trap: Making FixedDepositAccount inherit withdraw() from SavingsAccount and throwing UnsupportedOperationException violates LSP!
I — Interface Segregation (ISP) Clients should NOT be forced to depend on methods they do not use. Good: Split fat IBankAccount into IDepositable, IWithdrawable, ILoanable.
D — Dependency Inversion (DIP) High-level modules must depend on abstractions (interfaces), not concrete low-level classes. Good: LoanService depends on ICreditBureau interface (injected via Spring DI), not hardcoded CibilClient.
  • High Cohesion & Low Coupling: The golden rule of modular design—keep closely related responsibilities inside one class (High Cohesion) and minimize inter-class dependencies (Low Coupling).
  • Law of Demeter (Principle of Least Knowledge): "Talk only to your immediate friends"—avoid chained navigation like loan.getBorrower().getAddress().getPincode(); instead expose loan.getBorrowerPincode().
  • DRY / KISS / YAGNI: Don't Repeat Yourself (single source of truth), Keep It Simple, You Aren't Gonna Need It (avoid speculative over-engineering).

5.5 Gang of Four (GoF) Design Patterns — High-Yield Matrix

Guaranteed Paper III Favorite

The classic GoF book defines 23 Design Patterns in 3 categories: Creational (5), Structural (7), and Behavioral (11). Below are the 13 most frequently tested in Banking/Regulatory IT exams:

Category Pattern Core Intent (1-Line Recognition Key) Banking / Enterprise Example
Creational
(Object Creation)		 Singleton Ensures a class has only ONE instance globally with a global access point. CBS Config Manager, Logger, DB Connection Pool (use enum or Double-Checked Locking + volatile).
Factory Method Defines an interface for creating an object, letting subclasses decide which concrete class to instantiate. LoanFactory.create("MUDRA") vs. "MSE-GIFT".
Abstract Factory Creates families of related objects without specifying concrete classes. Creating matched Payment + KYC + Receipt objects per regulator region.
Builder Constructs a complex object step-by-step (avoids telescoping constructors). Building a 25-field MSME Loan Application / SQL Query object fluently.
Structural
(Class/Object Composition)		 Adapter Converts one incompatible interface into another expected by clients (Wrapper). Wrapping legacy ISO 8583 / SOAP CBS messages into modern OCEN REST JSON.
Decorator Attaches additional responsibilities dynamically at runtime without subclass explosion. Java BufferedInputStream(FileInputStream); stacking encryption + compression + logging on API streams.
Facade Provides a unified, simplified interface to a complex set of subsystems. Single approveMSMELoan() endpoint hiding CIBIL, GST, Udyam, and AML checks.
Proxy Acts as a surrogate/placeholder controlling access, caching, or lazy loading of another object. RBAC security proxy, Spring AOP transaction proxy, API rate-limit proxy.
Behavioral
(Object Interaction)		 Strategy Encapsulates a family of interchangeable algorithms selectable at runtime. Swapping EMI calculation or ML credit-scoring rules dynamically per loan product.
Observer Defines a one-to-many Pub/Sub dependency so dependents auto-update on state change. Loan disbursement event automatically notifies SMS, Email, Audit Log, and Ledger services.
Command Encapsulates a request as an object, enabling queuing, logging, and Undo/Redo. Queued financial transfer commands with compensating rollback transactions.
Template Method Defines an algorithm skeleton in a base class, deferring specific steps to subclasses. Base KYCWorkflow.verify() fixing step order while Aadhaar/PAN subclasses implement fetch steps.
Chain of Responsibility Passes a request along a chain of handlers until one handles it. Tiered loan-sanction approval limits (Branch Manager → Regional Head → Credit Committee) or HTTP auth filters.

5.6 OOAD, CRC Cards & Chidamber–Kemerer (CK) OO Metrics

High-Yield SE + OOP Bridge
  • CRC Cards (Class – Responsibility – Collaborator): Lightweight brainstorming cards used during Object-Oriented Analysis (OOA) to map domain nouns (Classes), verbs (Responsibilities), and interacting classes (Collaborators).
  • Chidamber & Kemerer (CK) Object-Oriented Metrics Suite (6 Classic Metrics):
    1. WMC (Weighted Methods per Class): Sum of cyclomatic complexities of all methods in a class → high WMC = hard to maintain/test.
    2. DIT (Depth of Inheritance Tree): Longest path from class to root (Object). High DIT = more reuse, but higher complexity & unpredictability.
    3. NOC (Number of Children): Direct immediate subclasses of a class. High NOC = high reuse, high impact if base class changes.
    4. CBO (Coupling Between Object classes): Count of other classes to which a class is coupled → LOWER is better.
    5. RFC (Response For a Class): Number of methods in the class + methods directly called by them → high RFC = harder debugging/testing.
    6. LCOM (Lack of Cohesion in Methods): Measures dissimilarity of methods sharing instance variables → LOWER is better (0 = maximally cohesive); high LCOM signals the class should be split (SRP!).

5.7 Worked OOAD & Design Pattern Case Scenarios (5 Exam Problems)

Applied Practice
Scenario 1: UML Use-Case Arrow Direction Trap (<<include>> vs. <<extend>>) Case: On SIDBI's portal, every "Submit Loan Application" MUST execute "Verify Udyam ID", and optionally triggers "Apply Green Subsidy (MSE-GIFT)" if the borrower owns solar equipment.
UML Modeling:
• Submit Loan Application - - <<include>> -> Verify Udyam ID (arrow points TO mandatory included step).
• Apply Green Subsidy - - <<extend>> -> Submit Loan Application (arrow points FROM optional extension TO base!).
Scenario 2: Applying OCP + Strategy + DIP to Banking Interest Calculation 
// Clean OCP + Strategy + DIP Refactor (Java/C#-style pseudocode)
interface InterestStrategy { BigDecimal calculate(BigDecimal principal, int months); }
class FixedRateStrategy implements InterestStrategy { /* ... */ }
class FloatingRepoStrategy implements InterestStrategy { /* ... */ }

class LoanProcessor {
  private final InterestStrategy strategy; // DIP: depends on abstraction
  LoanProcessor(InterestStrategy strategy) { this.strategy = strategy; }
  BigDecimal compute(BigDecimal p, int m) { return strategy.calculate(p, m); }
}
Adding a new Green Subvention Interest Rule requires ZERO changes to LoanProcessor (OCP satisfied!).
Scenario 3: Rapid GoF Pattern Identification (4 Banking Cases) • Legacy ISO 8583 binary ATM switch wrapped to expose JSON REST API → Adapter.
• One unified REST endpoint orchestrating CIBIL + GST + PAN + AML verification services → Facade.
• Disbursement event triggering SMS, Email, Webhook, and SIEM Audit subscribers → Observer.
• Loan sanction escalating from Officer (≤5L) → Manager (≤25L) → Committee (>25L) → Chain of Responsibility.
Scenario 4: Identifying Aggregation vs. Composition • BankBranch and Customer → Aggregation (if branch closes, customer accounts migrate; customers still exist).
• LoanContract and AmortizationRow → Composition (if loan contract is voided/deleted, its amortization schedule rows have no independent existence).
Scenario 5: Computing CK Metrics (DIT & NOC) Hierarchy: Account (root) has 2 direct children: DepositAccount and LoanAccount. LoanAccount has 3 direct children: TermLoan, WorkingCapitalLoan, GreenLoan.
Metrics: For LoanAccount: DIT = 1, NOC = 3. For GreenLoan: DIT = 2, NOC = 0.

5.8 Banking & SIDBI Enterprise OOP Context + 10-Mark Blueprint

Descriptive Edge

SIDBI's Udyamimitra plug-and-play platform onboards multiple ministerial MSME credit schemes with separate branded front-ends sharing a common backend—a textbook real-world application of OCP, Dependency Inversion, Factory/Strategy patterns, and Facade APIs. Similarly, integrating partner NBFCs and banks on GST Sahay (OCEN) relies heavily on Adapter layers to bridge diverse legacy CBS formats into unified JSON credit protocols.

Paper III (Part B) 10-Mark Descriptive Model Blueprint Probable Question: "Explain the SOLID design principles and demonstrate how at least three Gang of Four (GoF) design patterns improve maintainability and agility in an MSME digital lending platform." (10 Marks | 200 Words)
• Intro (25w): Frequent regulatory and MSME scheme updates demand loosely coupled, extensible OOP architectures.
• SOLID Summary (75w): Concisely define SRP, OCP, LSP, ISP, and DIP—emphasizing high cohesion and low coupling.
• 3 Banking GoF Patterns (80w): Strategy (pluggable scheme eligibility & interest engines), Adapter (bridging legacy CBS to OCEN/GST Sahay APIs), and Observer (decoupled SMS/email/audit notifications on loan sanction).
• Conclusion (20w): Together, SOLID and GoF patterns reduce regression defects and shorten time-to-market for new government MSME initiatives.

5.9 5-Minute Rapid Revision Sheet & 15 Exam-Level Practice MCQs

Last-Day Cram + Drill
  1. Encapsulation = implementation-level data hiding (private + getters/setters); Abstraction = design-level complexity hiding (interfaces).
  2. Compile-time polymorphism = Method/Operator Overloading (early binding); Runtime polymorphism = Method Overriding (late binding).
  3. UML visibility symbols: + public, - private, # protected, ~ package-private.
  4. Aggregation = Hollow Diamond (weak HAS-A, independent child lifecycle); Composition = Filled Black Diamond (strong PART-OF, child dies with parent).
  5. Generalization (IS-A) = solid line + hollow triangle; Realization (Implements) = dashed line + hollow triangle.
  6. Favor Composition over Inheritance to avoid the Fragile Base Class problem.
  7. SRP: One class = one reason to change. OCP: Open for extension, closed for modification.
  8. LSP: Subclasses must safely replace base classes without throwing unexpected exceptions or breaking contracts.
  9. ISP: Prefer small role-specific interfaces over one fat interface.
  10. DIP: Depend on abstractions, not concrete implementations (foundation of Dependency Injection).
  11. Law of Demeter: Talk only to immediate collaborators (no deep a.b().c().d() chains).
  12. UML 2.5 has 14 diagrams: 7 Structural (Static) + 7 Behavioral (Dynamic).
  13. Use Case trap: <<include>> = mandatory (Base → Included); <<extend>> = optional (Extension → Base!).
  14. Sequence Diagram emphasizes time-ordering across lifelines; Deployment Diagram maps software to physical hardware nodes.
  15. Activity Diagram uses Swimlanes and Fork/Join bars for parallel business workflows.
  16. GoF catalog = 23 patterns: 5 Creational, 7 Structural, 11 Behavioral.
  17. Singleton = single global instance; Factory Method = subclasses choose concrete class; Builder = step-by-step complex construction.
  18. Adapter = converts incompatible interface; Facade = simplifies complex subsystem; Decorator = dynamically wraps extra behavior.
  19. Proxy = surrogate for access control/caching/lazy init (same interface as real subject).
  20. Strategy = interchangeable runtime algorithms; Observer = 1-to-many Pub/Sub notifications.
  21. Command = request as object (Undo/Redo/Queue); Template Method = base-class skeleton + subclass steps.
  22. Chain of Responsibility = sequential approval/filter handlers.
  23. CRC Cards: Class – Responsibility – Collaborator (used in OO Analysis).
  24. CK Metrics: Lower CBO (Coupling) and Lower LCOM (Lack of Cohesion) indicate better OO design!
  25. High DIT (Depth of Inheritance Tree) increases reuse but reduces understandability and increases test complexity.
