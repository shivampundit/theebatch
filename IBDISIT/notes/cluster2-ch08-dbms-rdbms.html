Chapter 8: DBMS & RDBMS

Exhaustive exam-depth guide covering ANSI/SPARC 3-Schema architecture (SVG), ER-to-Relational mapping, Keys & Relational Algebra, Functional Dependencies & Normalization (1NF–5NF), SQL execution order / NULL traps / Window Functions, ACID & Conflict Serializability, SQL Isolation Levels / Strict 2PL / MVCC, WAL/ARIES Recovery & CAP/NoSQL, 7 worked numericals & SQL labs, banking CBS context, 25 one-liners, and 15 exam-level 5-option MCQs.

8.1 ANSI/SPARC 3-Schema Architecture, Data Independence & ER Modeling

Core Foundation
  • Physical Data Independence: Ability to change the Internal (Physical) Schema (e.g., adding a B+ Tree index, moving to NVMe SSD, compressing pages) WITHOUT modifying the Conceptual Schema or applications.
  • Logical Data Independence: Ability to change the Conceptual Schema (e.g., adding a new column or splitting a table) WITHOUT modifying External Views/user apps (harder to achieve!).
  • ER-to-Relational Table Conversion Rules (High-Yield MCQ!): • Weak Entity (lacks own primary key; double rectangle + double diamond identifying relationship) → table includes owner's PK as FK + partial key (discriminator).
    • 1:N Relationship → place PK of the 1-side as FK in the N-side table (NO extra table needed!).
    • M:N Relationship → MUST create a separate junction table containing PKs of both entities as composite PK.
    • Multivalued Attribute (double oval, e.g., multiple phone numbers) → MUST create a separate table.

8.2 Relational Model, Keys, Referential Integrity & Relational Algebra

  • Key Hierarchy: Super Key (SK) = any attribute set uniquely identifying a tuple → Candidate Key (CK) = minimal Super Key (no proper subset is a SK) → Primary Key (PK) = chosen CK (NOT NULL & UNIQUE) → Alternate Keys = remaining CKs → Foreign Key (FK) = references PK/Unique key of another (or same) table to enforce Referential Integrity (can be NULL unless constrained!).
  • Relational Algebra Core Operators (Procedural Query Language): • Selection (σ_cond(R)): Filters rows (commutative).
    • Projection (π_cols(R)): Picks columns and automatically eliminates duplicate rows (unlike SQL SELECT which keeps duplicates unless DISTINCT is used!).
    • Natural Join (R ⋈ S): Equi-join on all identically named attributes, removing duplicate join columns.
    • Division (R ÷ S): Answers "for ALL" universal quantifier queries (e.g., "Find borrowers who availed ALL green schemes"). Implemented in SQL via double NOT EXISTS.

8.3 Functional Dependencies, Normalization (1NF–5NF) & Decomposition

Guaranteed 2-Mark Topic

Armstrong's Axioms (Sound & Complete): Reflexivity (Y ⊆ X ⇒ X → Y), Augmentation (X → Y ⇒ XZ → YZ), Transitivity (X → Y, Y → Z ⇒ X → Z). Prime Attribute: Any attribute belonging to at least one Candidate Key.

Normal Form Strict Condition (for every non-trivial FD X → A) Eliminates Lossless & Dep-Preserving?
1NF Every cell holds atomic (indivisible) single values Multivalued / repeating groups Base relational requirement
2NF 1NF + No Partial Dependency (proper subset of CK → non-prime) Partial dependencies (auto-holds if every CK is single-column!) Lossless + Dep-Preserving
3NF 2NF + Either X is Superkey OR A is Prime Transitive dependencies (non-prime → non-prime) ALWAYS Lossless AND Dependency-Preserving
BCNF For EVERY non-trivial X → A, X MUST be a Superkey All FD-based redundancy (even prime-on-RHS traps!) Always Lossless, may NOT preserve all FDs!
4NF BCNF + No non-trivial Multivalued Dependency (X ↠ Y) unless X is SK Independent multi-valued attribute cross-products Lossless
5NF (PJNF) 4NF + No non-trivial Join Dependency not implied by CKs 3-way / n-way lossless join anomalies Lossless
Lossless-Join Decomposition Check (Binary Split R → R1, R2) A decomposition of R into R1 and R2 is Lossless if and only if their common attributes (R1 ∩ R2) form a superkey of AT LEAST ONE of them:
(R1 ∩ R2) → R1  OR  (R1 ∩ R2) → R2.

8.4 SQL Mastery: Execution Order, DELETE vs. TRUNCATE, NULL Traps & Window Functions

High Practical & MCQ Yield

Logical SQL Query Execution Order: 1. FROM / JOIN → 2. WHERE → 3. GROUP BY → 4. HAVING → 5. SELECT → 6. DISTINCT → 7. ORDER BY → 8. LIMIT / OFFSET. (Because WHERE runs before GROUP BY, it filters individual rows and CANNOT use SUM/COUNT; HAVING filters aggregated groups!)

Command Category WHERE Filter? Rollbackable? Fires Triggers & Resets Identity?
DELETE DML Yes Yes (row-by-row logged) Fires row triggers; keeps auto-increment counter
TRUNCATE DDL No (all rows) No (auto-commit in Oracle/MySQL; TX-safe in Postgres) Deallocates pages fast; resets identity; no row triggers
DROP DDL No No (auto-commit) Deletes data + table schema + indexes + permissions completely
  • SQL 3-Valued Logic (TRUE, FALSE, UNKNOWN) Traps: • col = NULL is ALWAYS UNKNOWN → always write col IS NULL.
    • COUNT(*) counts ALL rows including NULLs; COUNT(col), SUM, AVG IGNORE NULLs.
    • WHERE id NOT IN (10, 20, NULL) evaluates to EMPTY SET (0 rows!) because x != NULL is UNKNOWN.
  • Window Functions (Modern SQL Favorite): Compute aggregates WITHOUT collapsing rows! ROW_NUMBER() (1,2,3,4 — unique), RANK() (1,2,2,4 — skips rank on tie), DENSE_RANK() (1,2,2,3 — NO gap on tie, best for N-th highest salary/loan!), LAG() / LEAD() (access previous/next row for YoY NPA delta).

8.5 Transactions, ACID Properties, Conflict Serializability & Recoverability

Core Banking Theory
  • ACID Guarantees & Responsible Subsystems: Atomicity (all-or-nothing → Recovery Manager / Undo Log), Consistency (preserves DB invariants → Constraints + App logic), Isolation (concurrent TXs appear serial → Concurrency Control), Durability (committed writes survive crash → WAL Redo Log + Checkpoints).
  • Conflict Serializability: Two operations from different transactions on the same data item conflict iff at least one is a WRITE (R-W, W-R, W-W). Draw directed edge T_i → T_j whenever T_i's op precedes a conflicting op of T_j. Schedule is Conflict Serializable iff its Precedence Graph has NO CYCLE (is a DAG)!
  • View Serializability: Strictly broader than Conflict Serializability (every Conflict Serializable schedule is View Serializable, NOT vice versa—difference arises only when Blind Writes exist).
  • Recoverability Hierarchy (Innermost = Strongest): Strict ⊂ Cascadeless (ACA) ⊂ Recoverable. In a Strict schedule, a transaction cannot read OR write a data item modified by an uncommitted transaction (prevents both cascading aborts and dirty overwrites!).

8.6 SQL Isolation Levels, 2PL Locking & MVCC

High Descriptive & MCQ Yield
SQL Isolation Level Dirty Read (WR) Non-Repeatable Read (RW) Phantom Read (Range Insert)
Read Uncommitted Possible Possible Possible
Read Committed (Oracle / Postgres default) Prevented Possible Possible
Repeatable Read (MySQL InnoDB default) Prevented Prevented Possible (InnoDB prevents via Gap Locks!)
Serializable Prevented Prevented Prevented
  • Two-Phase Locking (2PL): Every transaction has a Growing Phase (acquire locks only, no releases) followed by a Shrinking Phase (release locks only, no acquisitions). • Basic 2PL: Guarantees Conflict Serializability, but NOT free from Deadlock or Cascading Rollbacks!
    • Strict 2PL: Holds all Exclusive (X) locks until Commit/Abort → guarantees Strict + Cascadeless schedules (still can deadlock).
    • Rigorous 2PL: Holds ALL Shared (S) and Exclusive (X) locks until Commit/Abort.
  • Deadlock Prevention (Timestamp-based): Wait-Die (Non-Preemptive): Older TX waits for younger; younger requesting older's lock dies (aborts).
    Wound-Wait (Preemptive): Older TX wounds (aborts) younger; younger waits for older.
  • MVCC (Multi-Version Concurrency Control): Keeps timestamped row snapshots so Readers never block Writers and Writers never block Readers (used by PostgreSQL, Oracle, MySQL InnoDB).

8.7 Crash Recovery (WAL / ARIES) & Distributed NoSQL / CAP Theorem

  • Write-Ahead Logging (WAL): Golden rule of durability—log records describing a change MUST be flushed to non-volatile disk BEFORE the modified data page is written to disk.
  • Deferred vs. Immediate Update: Deferred Update writes to DB only after commit (NO-UNDO / REDO); Immediate Update may write dirty pages before commit (UNDO / REDO).
  • ARIES Recovery Algorithm (3 Phases): (1) Analysis (scans forward from last checkpoint to find active TXs & Dirty Page Table), (2) Redo ("repeating history" forward from earliest RecLSN), (3) Undo (rolls back uncommitted loser TXs backward, writing Compensation Log Records — CLRs).
  • CAP Theorem (Eric Brewer): A distributed data store can simultaneously guarantee at most TWO of: Consistency (C), Availability (A), and Partition Tolerance (P). Since network partitions (P) are unavoidable, systems choose CP (strong consistency—banking ledgers, MongoDB, HBase, Spanner) or AP (eventual consistency / BASE—Cassandra, DynamoDB).
  • 4 NoSQL Families: Key-Value (Redis — session/OTP cache), Document (MongoDB — JSON MSME KYC payloads), Column-Family (Cassandra/HBase — massive time-series logs), Graph (Neo4j — AML/fraud ring traversal).

8.8 Worked Exam Numericals & SQL Query Lab (7 Problems)

Step-by-Step Solutions
Problem 1: Finding Candidate Keys & Highest Normal Form Relation: R(A, B, C, D) with FDs {A → B, B → C, C → D}.
Step 1 (Closure): A never appears on RHS → must be in every CK. A+ = {A, B, C, D} → Only CK = {A} (Prime: A; Non-prime: B, C, D).
Step 2 (NF Check): Single-attribute CK ⇒ automatically in 2NF. Check B → C: B is NOT a superkey and C is NOT prime (transitive dependency!) → fails 3NF. Highest NF = 2NF.
Problem 2: Lossless-Join Decomposition Test Relation: R(A, B, C, D) with {A → B, B → C, C → D} split into R1(A, B) and R2(B, C, D).
Check: Common attribute R1 ∩ R2 = {B}. Closure B+ = {B, C, D} = R2! Since (R1 ∩ R2) → R2, the decomposition is LOSSLESS.
Problem 3: SQL — 2nd Highest MSME Loan Amount per Branch 
WITH RankedLoans AS (
  SELECT branch_id, borrower_id, loan_amt,
         DENSE_RANK() OVER (PARTITION BY branch_id ORDER BY loan_amt DESC) AS rnk
  FROM msme_loans
)
SELECT branch_id, borrower_id, loan_amt FROM RankedLoans WHERE rnk = 2;
Why DENSE_RANK()? If two loans tie for 1st highest, RANK() skips to 3 (returning 0 rows for rnk = 2), while DENSE_RANK() cleanly assigns 2!
Problem 4: Precedence Graph Conflict Serializability Check Schedule S: R1(A), R2(A), W1(A), W2(A).
Conflicts: R1(A) → W2(A) gives edge T1 → T2; R2(A) → W1(A) gives edge T2 → T1.
Verdict: Cycle T1 ↔ T2 exists → NOT Conflict Serializable!
Problem 5: Wait-Die vs. Wound-Wait Decision Suppose T1 (older, TS=5) holds a lock on Account X and T2 (younger, TS=12) requests it.
• Wait-Die: Younger requests older's lock → T2 DIES (aborts & restarts with TS=12).
• Wound-Wait: Younger requests older's lock → T2 WAITS.
Problem 6: SQL COUNT(*) vs. COUNT(col) & LEFT JOIN Table Loans has 5 rows where column subsidy_amt is NULL in 2 rows. SELECT COUNT(*), COUNT(subsidy_amt) FROM Loans; outputs 5, 3.
Problem 7: Checkpoint Log Recovery (REDO vs. UNDO) Log shows: T1 committed BEFORE checkpoint; T2 active at checkpoint & committed BEFORE crash; T3 started after checkpoint & NOT committed before crash.
Recovery Action: Ignore T1 (already flushed at checkpoint); REDO T2; UNDO T3.

5-Minute Rapid Revision Sheet (25 High-Yield One-Liners)

  1. 3-Schema levels: External (View) → Conceptual (Logical) → Internal (Physical).
  2. Physical Data Independence shields Conceptual schema from storage/index changes.
  3. M:N ER relationships & multivalued attributes ALWAYS require a separate table.
  4. Candidate Key = minimal Super Key; Primary Key is strictly NOT NULL & UNIQUE.
  5. Relational Algebra Projection (π) eliminates duplicates; SQL SELECT keeps them unless DISTINCT is used.
  6. Relational Algebra Division (÷) solves "for ALL" universal queries.
  7. 2NF removes Partial Dependency; 3NF removes Transitive Dependency; BCNF requires every determinant X to be a Superkey.
  8. 3NF is ALWAYS Lossless AND Dependency-Preserving; BCNF is Lossless but may lose dependency preservation.
  9. 4NF eliminates Multivalued Dependencies (MVD); 5NF eliminates Join Dependencies.
  10. Binary decomposition (R1, R2) is lossless iff (R1 ∩ R2) → R1 OR (R1 ∩ R2) → R2.
  11. SQL Execution Order: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT.
  12. DELETE is DML (row-logged, rollbackable); TRUNCATE & DROP are DDL (fast, auto-commit).
  13. COUNT(*) includes NULLs; COUNT(col) ignores NULLs; NOT IN (..., NULL) returns 0 rows!
  14. DENSE_RANK() leaves no gaps on ties (best for N-th highest queries).
  15. Conflict operations: different TXs, same item, at least one WRITE.
  16. Schedule is Conflict Serializable iff its Precedence Graph is ACYCLIC.
  17. Recoverability hierarchy: Strict ⊂ Cascadeless ⊂ Recoverable.
  18. Read Committed prevents Dirty Reads; Repeatable Read prevents Dirty + Non-Repeatable; Serializable prevents Phantoms too.
  19. Basic 2PL guarantees conflict serializability, NOT deadlock freedom; Strict 2PL holds all X-locks until commit (cascadeless).
  20. Wait-Die = non-preemptive (younger dies); Wound-Wait = preemptive (older wounds younger).
  21. MVCC lets readers and writers run concurrently without blocking each other via row snapshots.
  22. WAL (Write-Ahead Logging) flushes log to disk BEFORE dirty data pages.
  23. ARIES 3 recovery phases: Analysis → Redo → Undo.
  24. CAP Theorem: Under Partition (P), choose CP (Banking/ACID) or AP (Eventual/BASE).
  25. 4 NoSQL types: Key-Value (Redis), Document (MongoDB), Column-Family (Cassandra), Graph (Neo4j).
