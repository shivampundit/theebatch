16.1 Application Architectures: Monolith vs. Microservices vs. Serverless

Architecture Core
Pattern Key Strengths Trade-Offs / Exam Traps
Monolith Simple dev/debug, local ACID joins, zero network hop latency Single deployment unit; must scale entire app; one memory leak crashes all modules
Microservices Independent scaling, polyglot tech stacks, fault isolation, Database-per-Service Distributed complexity; NO cross-service ACID joins → uses Saga Pattern (local TXs + compensating rollbacks!)
CQRS Separates Command (Write) model from Query (Read) model Allows read-heavy MSME dashboards to scale independently of write-heavy CBS ledgers
Serverless (FaaS) Auto-scales to zero, pay-per-execution (e.g., PDF KYC OCR trigger) Cold-Start latency, vendor lock-in, unsuitable for long-running stateful jobs

16.2 The Twelve-Factor App Methodology (Cloud-Native Checklist)

  • Key Factors Tested in IT Exams: (1) Codebase: One repo tracked in Git, many deploys (Dev/UAT/Prod). (2) Dependencies: Explicitly declared & isolated (pom.xml, requirements.txt). (3) Config: Store environment config & secrets in Environment Variables / Vault—NEVER hardcode credentials in source code! (4) Processes: Execute apps as Stateless, Share-Nothing processes (persist session state in external Redis/DB so horizontal scaling works!). (5) Disposability: Fast startup & graceful shutdown on SIGTERM. (6) Dev/Prod Parity: Keep dev, staging, and prod environments identical (via containers). (7) Logs: Treat logs as unbuffered event streams (stdout) routed to SIEM/ELK rather than local disk files.

16.3 Frontend Architectures (MVC/SPA/SSR/PWA) & Browser Storage Traps

High Security & Web MCQ Zone
  • Architectural Patterns: MVC (Model = data/rules, View = UI, Controller = request coordinator) vs. MVVM (ViewModel binds UI state declaratively—Angular/Vue/Android) vs. Hexagonal / Clean Architecture (Ports & Adapters isolating core domain logic from DB/HTTP frameworks).
  • Web Rendering Modes: SPA / CSR (Client-Side Rendering in JS — fast transitions, slower initial load) vs. SSR (Server-Side Rendering — fast First Contentful Paint & SEO) vs. PWA (Progressive Web App) (uses Service Workers + Web App Manifest for offline caching & installability).
Browser Storage Capacity Sent on Every HTTP Request? XSS / Security Verdict
Cookies ~4 KB Yes (automatic) SAFEST for Auth Tokens when flags HttpOnly (blocks JS/XSS), Secure (HTTPS only), and SameSite=Strict (blocks CSRF) are set!
localStorage ~5–10 MB No Persists across restarts, but readable by any JS → vulnerable to XSS (do NOT store sensitive auth tokens!).
sessionStorage ~5–10 MB No Cleared automatically when browser tab closes; still JS-readable.
IndexedDB Hundreds of MB+ No Asynchronous transactional client-side NoSQL store for offline PWAs.

16.4 Backend Scalability: Caching Patterns, Kafka/Queues & Sharding

High System-Design Yield
  • Caching Strategies (Redis / Memcached): • Cache-Aside (Lazy Loading): App checks cache → on miss, reads DB → writes to cache with TTL (resilient if cache crashes; first request is a miss).
    • Write-Through: App writes to Cache & DB synchronously (always consistent, higher write latency).
    • Write-Back (Write-Behind): App writes to Cache only, async flush to DB (fastest writes, risk of data loss on crash—avoid for banking ledgers!).
    • Cache Stampede (Thundering Herd): Thousands of requests hit DB simultaneously when a hot key expires → fixed via mutex lock / probabilistic early refresh.
  • RabbitMQ vs. Apache Kafka: RabbitMQ (Message Broker): Smart broker, push-based routing, deletes message once acknowledged (great for task queues). Apache Kafka (Distributed Event Log): Append-only partitioned log, pull-based Consumer Groups, retains messages for configurable days enabling event replay & million-msg/sec throughput. Failed unprocessable messages move to a Dead-Letter Queue (DLQ).
  • Database Scaling: Read Replicas (scale read-heavy queries with eventual lag) → Sharding (Horizontal Partitioning) splits rows across independent DB nodes by shard key (e.g., region_id).

16.5 Docker, Kubernetes (K8s) Orchestration & Infrastructure as Code

Modern Cloud-Native Core
  • Docker Best Practices: Use Multi-Stage Builds (compile in heavy SDK image, copy only binary to slim distroless/Alpine image), run as a non-root user, scan images for CVEs before pushing to private registry.
  • Kubernetes Core Primitives (Must-Know!): • Pod: Smallest deployable scheduling unit in K8s (wraps 1 or tightly coupled sidecar containers sharing IP & volume).
    • Deployment / ReplicaSet: Maintains desired number of healthy Pods (self-healing + rolling updates/rollbacks).
    • Service: Stable virtual IP & internal DNS load-balancing across ephemeral Pod IPs.
    • Ingress: L7 HTTP/HTTPS routing & TLS termination into cluster services.
    • HPA (Horizontal Pod Autoscaler): Automatically scales Pod replica count based on CPU/memory/custom RPS metrics.
  • Infrastructure as Code (IaC): Managing servers, VPCs, and K8s clusters declaratively via version-controlled code (Terraform, Ansible)—eliminates manual "snowflake servers" and configuration drift.

16.6 Observability (3 Pillars) & SLI / SLO / SLA Reliability Math

  • Three Pillars of Observability: 1. Metrics (numeric time-series: CPU, RPS, p95/p99 latency, error rate — Prometheus/Grafana); 2. Logs (structured JSON timestamped events — ELK/SIEM); 3. Distributed Traces (tracks one request across 10 microservices via a shared trace_id — OpenTelemetry/Jaeger).
  • SLI vs. SLO vs. SLA: • SLI (Indicator): Actual measured metric (e.g., 99.94% of API calls succeeded under 300ms).
    • SLO (Objective): Internal engineering target (e.g., 99.9% → defines an Error Budget = 0.1%).
    • SLA (Agreement): External legal contract with customers/partners carrying financial/remedy penalties if breached (always looser than internal SLO!).

16.7 Worked Application Architecture Scenarios & Math (6 Cases)

Applied Practice
Scenario 1: Monthly Error Budget Calculation (99.9% vs. 99.99% SLO) Assume a 30-day month = 30 × 24 × 60 = 43,200 minutes.
• At 99.9% ("Three Nines"): Allowed downtime = 0.001 × 43,200 = 43.2 minutes/month.
• At 99.99% ("Four Nines"): Allowed downtime = 0.0001 × 43,200 = 4.32 minutes/month!
Scenario 2: Distributed Transaction Across Microservices (Saga Pattern) Loan Service approves sanction → Ledger Service debits pool → Payment Service fails due to bank timeout. How do you maintain consistency without distributed 2PC locks?
Answer: Trigger Saga Compensating Transactions (Ledger credits pool back → Loan Service reverts status to Disbursal_Failed) via Kafka events!
Scenario 3: Fixing Stateful Session Failure Behind a Load Balancer Users randomly get logged out when the bank scales its portal from 1 server to 4 servers behind Nginx.
Root Cause & Fix: Session state was stored in local server RAM (violating 12-Factor #6!). Externalize sessions into a shared Redis cluster so all 4 stateless app nodes serve any user seamlessly.
Scenario 4: Choosing Caching Policy for Banking Ledgers vs. Static Master Data • MSME Scheme Master List (read 100k/day, updated monthly) → Cache-Aside with TTL.
• Live Account Balances → NEVER Write-Back (crash loses money!); use direct ACID DB writes (or strict Write-Through invalidation).
Scenario 5: Modernizing Legacy Monolith Without Big-Bang Risk Place an API Gateway in front of the monolith and migrate one module at a time (KYC → Eligibility → Disbursement) to microservices → Strangler Fig Pattern.
Scenario 6: Poison-Pill Message Handling in Event Streams A malformed GST JSON event crashes a consumer repeatedly in an infinite retry loop, stalling the entire queue.
Fix: Route messages failing after N retries to a Dead-Letter Queue (DLQ) for manual/automated inspection while healthy events keep flowing.

16.8 SIDBI Cloud-Native Modernization Blueprint (10-Mark Descriptive)

Paper III Part B Edge
10-Mark Model Answer Outline (200 Words) Question: "How should SIDBI migrate a legacy monolithic MSME lending portal to a resilient, scalable cloud-native microservices architecture?"
• Intro (25w): Monolithic portals struggle with peak scheme-launch traffic, slow release cycles, and single-point failures.
• Phased Migration (60w): Apply the Strangler Fig Pattern behind an API Gateway, peeling off bounded contexts (KYC, Scoring, Disbursement, Notifications) into stateless 12-Factor microservices with Database-per-Service.
• Resilience & Ops (90w): Deploy containerized services on Kubernetes (HPA auto-scaling, non-root multi-stage images, Terraform IaC), decouple workflows via Apache Kafka + Saga compensating transactions + DLQ, offload sessions/master data to Redis, and implement OpenTelemetry Metrics/Logs/Traces.
• Conclusion (25w): Paired with RBI AIFI DevSecOps and BCP/DR governance, this delivers elastic, fault-isolated MSME credit delivery.

16.9 5-Minute Rapid Revision Sheet & 15 Exam-Level Practice MCQs

Last-Day Cram + Drill
  1. Microservices enforce Database-per-Service for loose coupling and independent scaling.
  2. Distributed consistency across microservices uses the Saga Pattern (local TXs + compensating rollbacks) instead of blocking 2PC.
  3. CQRS separates Command (Write) models from Query (Read) models.
  4. Strangler Fig Pattern incrementally migrates a legacy monolith to microservices behind an API Gateway.
  5. Serverless (FaaS) scales to zero automatically but suffers Cold-Start latency.
  6. 12-Factor App: Store config/secrets in Environment Variables / Secret Vaults, NEVER hardcoded in Git!
  7. 12-Factor App: Application processes must be Stateless (externalize sessions to Redis/DB).
  8. PWA relies on Service Workers + Web App Manifest for offline functionality.
  9. Browser auth tokens belong in HttpOnly; Secure; SameSite Cookies—NEVER in localStorage (XSS-readable!).
  10. Cache-Aside (Lazy Loading) populates cache on miss; Write-Back risks data loss on crash.
  11. Cache Stampede happens when many requests hit the DB simultaneously after a hot key expires.
  12. Apache Kafka is a distributed append-only partitioned log supporting event replay; RabbitMQ is a smart push broker.
  13. Unprocessable "poison-pill" queue messages are isolated in a Dead-Letter Queue (DLQ).
  14. Sharding partitions database rows horizontally across independent servers.
  15. Docker Multi-Stage Builds shrink image size and remove build tools from production containers.
  16. Pod is the smallest deployable scheduling unit in Kubernetes (not a bare container).
  17. K8s Deployment ensures desired Pod replicas; Service gives stable virtual IP; Ingress handles L7 HTTP/TLS routing.
  18. HPA (Horizontal Pod Autoscaler) scales Pods out/in automatically based on load metrics.
  19. IaC (Terraform / Ansible) eliminates manual server configuration drift.
  20. Three Pillars of Observability: Metrics, Logs, and Distributed Traces (OpenTelemetry).
  21. SLI = measured value; SLO = internal target (Error Budget); SLA = external contract with penalty.
  22. 99.9% ("Three Nines") allows 43.2 min/month downtime; 99.99% allows 4.32 min/month.
  23. SSR improves initial load speed and SEO over pure client-side SPAs.
  24. Hexagonal Architecture (Ports & Adapters) isolates business domain logic from external frameworks.
  25. IndexedDB stores large structured datasets asynchronously inside the browser for offline apps.
