15.1 API Architectural Styles: REST vs. SOAP vs. GraphQL vs. gRPC

Core Comparison
Feature REST SOAP GraphQL gRPC
Protocol / Style Architectural style over HTTP/HTTPS Strict XML protocol (HTTP/SMTP/JMS) Query language over HTTP (single /graphql) High-performance RPC over HTTP/2
Payload Format JSON (primarily), XML, text Strictly XML (Envelope/Header/Body) JSON Protocol Buffers (Binary)
Contract / Schema OpenAPI (Swagger) 3.x WSDL + XSD GraphQL SDL (strongly typed) .proto IDL files
Key Strength Simplicity, HTTP caching, universal public APIs Built-in WS-Security, ACID WS-AtomicTransaction Eliminates over-fetching & under-fetching Ultra-low latency, bi-directional streaming
Banking Use Case OCEN, GST Sahay, Account Aggregator, Partner APIs Legacy CBS, SWIFT/SFMS enterprise integrations Aggregating complex MSME mobile dashboard views Internal high-speed microservice-to-microservice calls

Roy Fielding's 6 REST Constraints: (1) Client–Server separation, (2) Statelessness (server stores NO client session state between requests), (3) Cacheability, (4) Uniform Interface (Resource URIs + HATEOAS), (5) Layered System, (6) Code-on-Demand (optional). WebSockets (wss://): Persistent full-duplex TCP connection for real-time market tickers, live fraud alerts, or chat.

  • Pagination: Offset/Limit (?offset=1000&limit=20) degrades on deep pages and skips/duplicates rows if live inserts occur; Cursor (Keyset) Pagination (?after_id=TXN9981&limit=20) uses B+ Tree index seeks for constant O(1) performance on live banking ledgers.
  • API Versioning: URI Path (/api/v1/loans — most common), Custom Header (X-API-Version: 2), or Content Negotiation (Accept: application/vnd.sidbi.v2+json).

15.3 API Security: OAuth 2.0, OIDC, JWT & Mutual TLS (mTLS)

High Paper III Objective & Descriptive Yield
  • OAuth 2.0 vs. OpenID Connect (OIDC): OAuth 2.0 is strictly for Authorization (delegated scoped access via Access Token); OIDC is an identity layer built ON TOP of OAuth 2.0 providing Authentication via an ID Token!
  • OAuth 2.0 Key Grant Types: • Authorization Code + PKCE: Mandatory modern flow for user-facing web/mobile apps (PKCE prevents authorization-code interception!).
    • Client Credentials: Machine-to-Machine (M2M) server-to-server calls (no human user present).
  • JWT (JSON Web Token) Traps: Format = Base64URL(Header).Base64URL(Payload).Signature. JWTs are SIGNED (tamper-proof), NOT ENCRYPTED (anyone can decode the payload—never store passwords/PAN inside unless using JWE!). Always pin allowed algorithms server-side to block the alg: none bypass.
  • mTLS (Mutual TLS): Standard TLS authenticates only the server; mTLS verifies X.509 certificates on BOTH Client and Server—mandatory for RBI/NPCI/OCEN B2B banking APIs!

15.4 API Gateways, Rate Limiting, Circuit Breakers & Webhooks

  • Rate-Limiting Algorithms (Prevents DoS & Quota Abuse → returns HTTP 429 Too Many Requests): • Token Bucket: Tokens refill at steady rate up to bucket capacity; permits short controlled bursts.
    • Leaky Bucket: Queue drains at a strict constant outflow rate (smooths spiky traffic; drops overflow).
    • Sliding Window Counter: Fixes the boundary-spike flaw of Fixed Window counters.
  • Circuit Breaker Pattern (Resilience): Prevents cascading failure when a downstream credit bureau (CIBIL/GSTN) stalls. Three states: Closed (normal) → Open (fail-fast after error threshold) → Half-Open (sends probe requests to test recovery). Pair with Exponential Backoff + Jitter on retries.
  • Webhooks vs. Polling: Instead of clients repeatedly polling GET /status every second, the server pushes an HTTP POST event callback to the client's registered URL when loan sanction finishes—secured with an HMAC-SHA256 signature header to verify authenticity.

15.6 India's Open-Banking & DPI API Ecosystem (AA, OCEN & GST Sahay)

2025–2026 SIDBI Exam Gold
  • Account Aggregator (AA) Ecosystem (RBI NBFC-AA Framework / ReBIT APIs): • FIP (Financial Information Provider): Banks, GSTN, Depositories holding customer data.
    • FIU (Financial Information User): Lenders (like SIDBI/NBFCs) requesting consented financial data.
    • AA (Account Aggregator): Data-blind consent manager—transmits end-to-end encrypted data only after explicit digital consent artifact; AA CANNOT read or store financial data!
  • OCEN (Open Credit Enablement Network) & SIDBI GST Sahay: Open standardized REST API protocol decoupling Loan Service Providers (LSPs — e.g., GST/e-commerce platforms) from Lenders, enabling completely paperless, presence-less, cash-flow-based MSME invoice financing (SIDBI Digital Initiatives).

15.7 Worked API Design & Troubleshooting Scenarios (6 Cases)

Applied Practice
Scenario 1: Preventing Duplicate Disbursement on Network Timeout A partner NBFC calls POST /v1/loans/disburse; the server commits the payout, but the response times out. The client retries. How do you stop a second payout?
Fix: Require a client-generated UUID Idempotency-Key header stored with a UNIQUE DB constraint; retries return the cached original response without re-executing!
Scenario 2: Spotting BOLA vs. Mass Assignment (a) Changing URL /invoices/88 to /invoices/89 to read another MSME's invoice → API1: BOLA.
(b) Sending {"mobile":"9999...", "credit_limit": 9999999} to PATCH /profile and overwriting credit_limit → API3: Mass Assignment.
Scenario 3: Choosing the Optimal API Style • Public MSME partner onboarding API → REST (OpenAPI + JSON).
• Internal 50,000-RPS fraud-scoring microservice call → gRPC (HTTP/2 + Protobuf).
• Live bi-directional market feed → WebSockets.
Scenario 4: Token Bucket Rate Limiter Math An API Gateway configures a Token Bucket with capacity 100 tokens and refill rate 10 tokens/sec. Starting full, a partner fires 120 simultaneous requests in 1 second.
Result: First 100 requests succeed (burst absorbed); remaining 20 receive HTTP 429 Too Many Requests.
Scenario 5: Auditing a Flawed JWT Developer puts {"pan":"ABCDE1234F","balance":500000} inside a standard JWS JWT payload assuming "it's encrypted".
Flaw: JWT payload is merely Base64URL-encoded plaintext—trivially decoded by anyone without a key! Keep JWT payloads minimal (sub, role, exp, jti).
Scenario 6: Account Aggregator Role Mapping An MSME gives consent for SIDBI to pull 12 months of bank statements from SBI via an RBI-licensed Aggregator.
Roles: SBI = FIP; Aggregator = AA (data-blind); SIDBI = FIU.

15.8 SIDBI Open-Credit API Security Blueprint (10-Mark Descriptive)

Paper III Part B Edge
10-Mark Model Answer Outline (200 Words) Question: "Outline a defense-in-depth API architecture for an open-credit MSME lending platform like SIDBI's GST Sahay integrating with Account Aggregators and partner NBFCs."
• Intro (25w): Open-credit protocols (OCEN/AA) expose core lending workflows to external LSPs, making API security mission-critical.
• Transport & Auth (65w): Enforce TLS 1.3 + mTLS for partner identity, OAuth 2.0 Client Credentials with short-lived RS256 JWTs, and HMAC-signed webhooks.
• Gateway & OWASP Controls (85w): Deploy centralized API Gateway for schema validation (OpenAPI), Token-Bucket rate limiting (`429`), strict BOLA/BFLA authorization, DTO allow-lists against Mass Assignment, Idempotency Keys on `POST` disbursements, and Circuit Breakers for resilient bureau calls.
• Conclusion (25w): Continuous API inventory discovery eliminates Zombie APIs while centralized SIEM logging satisfies CERT-In and DPDP 2025 mandates.

15.9 5-Minute Rapid Revision Sheet & 15 Exam-Level Practice MCQs

Last-Day Cram + Drill
  1. REST's key constraint: Statelessness (each request carries full auth/context; no server session).
  2. SOAP strictly uses XML + WSDL + WS-Security; gRPC uses HTTP/2 + Binary Protocol Buffers.
  3. GraphQL solves over-fetching & under-fetching via a single typed endpoint.
  4. WebSockets provide persistent full-duplex TCP connections for real-time push updates.
  5. HTTP Idempotency: GET, PUT, DELETE are Idempotent; POST is NOT idempotent (needs Idempotency-Key!).
  6. Cursor Pagination outperforms Offset Pagination on live, rapidly changing banking tables.
  7. OAuth 2.0 = Authorization (Access Token); OIDC = Authentication (ID Token on top of OAuth 2.0).
  8. OAuth 2.0 Authorization Code + PKCE for mobile/SPA; Client Credentials for server-to-server M2M.
  9. JWT = Header.Payload.Signature (Base64URL-encoded, signed NOT encrypted; block alg: none!).
  10. mTLS (Mutual TLS) authenticates BOTH client and server using X.509 certificates.
  11. Token Bucket allows bursts; Leaky Bucket enforces strict constant outflow rate; excess returns HTTP 429.
  12. Circuit Breaker states: Closed → Open → Half-Open (prevents cascading timeouts).
  13. Retry storms are prevented via Exponential Backoff with Jitter.
  14. Webhooks eliminate polling; verify authenticity using HMAC-SHA256 signature headers.
  15. API1: BOLA (IDOR) is the #1 OWASP API vulnerability (accessing another user's object ID).
  16. API3: Mass Assignment = attacker injecting privileged fields into JSON payloads (fix: DTO allow-list).
  17. API5: BFLA = low-privilege user invoking admin endpoints; API9 = forgotten Zombie/Shadow APIs.
  18. OpenAPI (Swagger) defines machine-readable REST contracts for docs, mocking, and gateway validation.
  19. Account Aggregator (AA) is a data-blind RBI-regulated consent broker between FIP and FIU.
  20. In AA flow: FIP = data holder (bank/GSTN); FIU = data consumer (lender like SIDBI).
  21. OCEN standardizes open-credit APIs powering SIDBI GST Sahay invoice-based lending.
  22. CORS (Cross-Origin Resource Sharing) is a browser-enforced header policy (Access-Control-Allow-Origin).
  23. PUT replaces the entire resource; PATCH applies a partial update.
  24. 401 Unauthorized = missing/invalid token; 403 Forbidden = valid token but insufficient scope/role.
  25. Never transmit sensitive PII, OTPs, or tokens inside URL query parameters (they leak into server/proxy logs).
