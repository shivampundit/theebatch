13.1 Classical & Evolutionary SDLC Process Models

Core Foundation
SDLC Model Core Principle Best Suited For Key Limitation / Exam Trap
Waterfall Linear sequential phases (Req → Design → Code → Test → Maintain) Stable, crystal-clear, frozen requirements Working software appears only at the very end; costly late requirement changes
V-Model Verification (left) paired with Validation (right) at every level Safety-critical & regulated banking/medical software Req ↔ UAT; HLD ↔ Integration/System; LLD ↔ Unit Testing
Spiral (Barry Boehm) Iterative + Explicit Risk Analysis in every loop (4 quadrants) Large, expensive, high-risk mission-critical projects Requires specialized risk-assessment expertise; high management overhead
Incremental Delivers functional core first, adds increments iteratively Early ROI delivery when core requirements are known Needs clean modular architecture upfront
RAD Component-based rapid assembly in 60–90 day timeboxes Modular business/UI apps with tight deadlines Unsuitable for high-technical-risk or non-modular systems

13.2 Agile, Scrum, Kanban, XP & Modern DevSecOps CI/CD

High Descriptive & Modern IT Yield
  • Scrum Framework (3-3-5 Rule): 3 Roles: Product Owner (owns Product Backlog/ROI), Scrum Master (servant-leader removing impediments), Developers. 3 Artifacts: Product Backlog, Sprint Backlog, Increment. 5 Events: Sprint (1–4 weeks), Sprint Planning, Daily Scrum (15 min), Sprint Review (demo to stakeholders), Sprint Retrospective (team process improvement).
  • Kanban vs. XP: Kanban uses visual boards + strict WIP (Work-In-Progress) limits for continuous pull flow (no fixed sprints). XP (Extreme Programming) emphasizes Test-Driven Development (TDD: Red → Green → Refactor), Pair Programming, and Continuous Integration.
  • Zero-Downtime Deployment Strategies: • Blue-Green: Two identical prod environments; instant router flip & instant rollback.
    • Canary Release: Route small % (e.g., 5%) of live traffic to new version before full rollout.
    • SAST vs. DAST: SAST = White-box static source-code analysis (early in CI); DAST = Black-box dynamic testing against running app.

13.3 Project Estimation: COCOMO, Function Points (FP) & PERT/CPM

Guaranteed 2-Mark Formulas
Basic COCOMO Mode a b c d Project Profile
Organic2.41.052.50.38Small, experienced team; simple business apps
Semi-Detached3.01.122.50.35Medium complexity; mixed team experience
Embedded3.61.202.50.32Tight hardware, real-time, or strict regulatory constraints
  • Basic COCOMO Formulas: Effort (E) = a · (KLOC)^b (Person-Months) • Dev Time (D) = c · (E)^d (Months) • Avg Staff = E / D.
  • Function Point Analysis (Albrecht): Programming-language independent sizing! Counts 5 parameters: External Inputs (EI), External Outputs (EO), External Inquiries (EQ), Internal Logical Files (ILF), External Interface Files (EIF) → weighted sum = UFP. FP = UFP × [0.65 + 0.01 × ΣF_i] (where 14 complexity factors F_i ∈ [0..5], so VAF ∈ [0.65, 1.35]).
  • PERT / CPM Scheduling: Expected Time T_e = (O + 4M + P) / 6 • Std Dev σ = (P - O) / 6. Critical Path = LONGEST duration path through the network with Zero Float/Slack—any delay on it delays the entire project!

13.4 Software Testing: Verification vs. Validation, White-Box & Black-Box

Top Paper III Objective Zone
  • Verification vs. Validation (Boehm): Verification = "Are we building the product RIGHT?" (Static checks without running code: Reviews, Walkthroughs, Inspections). Validation = "Are we building the RIGHT product?" (Dynamic code execution against user needs).
  • White-Box (Structural) Testing & Cyclomatic Complexity: Coverage hierarchy: Statement < Branch/Decision < Condition < Path Coverage. McCabe's Cyclomatic Complexity V(G) = minimum number of linearly independent basis paths: V(G) = E - N + 2 = P + 1 = R (Edges E, Nodes N, Predicate/decision nodes P, Planar Regions R).
  • Black-Box (Functional) Testing: • Equivalence Partitioning: Divide input domain into valid/invalid equivalence classes; test 1 representative per class.
    • Boundary Value Analysis (BVA): Defects cluster at boundaries (min, min+, nom, max-, max) → 4n + 1 normal test cases (or 6n + 1 robust BVA including min-, max+) for n inputs.
  • Integration & System Testing Traps: • Top-Down Integration requires Stubs (dummy lower modules); Bottom-Up Integration requires Drivers (dummy callers).
    • Alpha Testing: Done by users at the developer's controlled site. Beta Testing: Done by real end-users at the customer's live environment.
    • Regression Testing: Re-running test suites after a fix/change to confirm existing features didn't break.
    • Smoke Testing (wide & shallow build-health check) vs. Sanity Testing (narrow & deep check on one patched feature).

13.5 Maintenance Taxonomy, SCM, CMMI & Reliability (MTBF / Availability)

Maintenance Type Purpose Typical Cost Share
1. CorrectiveFixing residual production bugs/defects~20%
2. AdaptiveAdapting to OS upgrades, hardware, or new RBI/tax regulations~25%
3. PerfectiveAdding new features, UI enhancements & performance optimization~50%+ (LARGEST!)
4. PreventiveCode refactoring & reverse engineering to curb technical debt~5%
  • CMMI 5 Maturity Levels (Staged): 1. Initial (Ad-hoc) → 2. Managed → 3. Defined → 4. Quantitatively Managed → 5. Optimizing.
  • Reliability & Availability Formulas: MTBF = MTTF + MTTR (Mean Time Between Failures = Mean Time To Failure + Mean Time To Repair).
    Availability = MTTF / (MTTF + MTTR) = MTTF / MTBF.
  • Software Configuration Management (SCM): Controls change via Baselines, Version Control (Git), and Change Control Board (CCB) approvals.

13.6 Worked Exam Numericals (7 Step-by-Step SE Problems)

2-Mark Scoring Zone
Numerical 1: McCabe's Cyclomatic Complexity V(G) Problem: A loan-sanction function's Control Flow Graph has N = 10 nodes and E = 13 edges (single connected component). Find V(G).
Formula: V(G) = E - N + 2 = 13 - 10 + 2 = 5 independent basis paths (equivalent to 4 binary predicate nodes + 1).
Numerical 2: Function Point (FP) Calculation Given: Unadjusted Function Points UFP = 250; sum of 14 complexity factors ΣF_i = 45.
VAF: 0.65 + 0.01(45) = 1.10. Adjusted FP: 250 × 1.10 = 275 FP.
Numerical 3: Basic COCOMO Estimation (Organic Mode) Given: KLOC = 10 (Organic: a = 2.4, b = 1.05; assume 10^1.05 ≈ 11.22).
Effort: E = 2.4 × 11.22 = 26.93 Person-Months.
Numerical 4: Boundary Value Analysis (BVA) Test Cases Problem: An EMI calculator takes n = 3 independent inputs (Principal, Rate, Tenure). Find normal BVA and robust BVA test counts.
Normal BVA: 4(3) + 1 = 13 cases. Robust BVA: 6(3) + 1 = 19 cases.
Numerical 5: PERT Expected Duration & Standard Deviation Given: Optimistic O = 4 days, Most Likely M = 7 days, Pessimistic P = 16 days.
T_e = (4 + 4(7) + 16) / 6 = 48 / 6 = 8 days. σ = (16 - 4) / 6 = 2 days.
Numerical 6: Availability & MTBF Given: Banking API Gateway has MTTF = 1980 hours and MTTR = 20 hours.
MTBF = 1980 + 20 = 2000 hrs. Availability = 1980 / 2000 = 99.0%.
Numerical 7: Integration Testing Direction Testing the bottom-level EncryptionUtil and DBConnector before the main LoanService exists uses Bottom-Up Integration and requires writing Drivers.

13.7 Banking & SIDBI DevSecOps Context + 10-Mark Blueprint

Descriptive Edge

Under RBI's IT Governance Master Direction, financial institutions must enforce strict Segregation of Duties (SoD) across Development, QA/UAT, and Production environments—developers NEVER push directly to production without automated SAST/DAST/SBOM security gates, peer code review, UAT sign-off, and Change Advisory Board (CAB) approval for portals like SIDBI Udyamimitra & GST Sahay.

Paper III (Part B) 10-Mark Descriptive Model Blueprint Probable Question: "How does adopting a DevSecOps CI/CD pipeline with Shift-Left security testing improve release velocity without compromising RBI change-management controls in a banking IT environment?" (10 Marks | 200 Words)
• Intro (25w): Traditional siloed Waterfall releases cause months-long delays and late security defect discovery.
• Shift-Left DevSecOps Controls (85w): Embed secret scanning, SAST, SCA/SBOM generation, automated unit/regression tests, and DAST directly inside CI pipelines—catching OWASP flaws before UAT.
• RBI Change Governance (70w): Enforce Git branch protection, Segregation of Duties (automated CD service accounts, no developer prod access), mandatory CAB/UAT approval gates, and Blue-Green/Canary rollbacks with immutable audit logs.
• Conclusion (20w): DevSecOps turns compliance from a manual bottleneck into repeatable, auditable automation.

13.8 5-Minute Rapid Revision Sheet (25 High-Yield One-Liners)

Last-Day Cram
  1. Spiral Model (Barry Boehm) is explicitly Risk-Driven (4 quadrants per loop).
  2. V-Model pairs every dev phase with a test phase (Req↔UAT, HLD↔Integration, LLD↔Unit).
  3. Scrum = 3 Roles (PO, SM, Devs), 3 Artifacts, 5 Events (Daily Scrum = 15 min).
  4. Kanban limits Work-In-Progress (WIP) in a continuous pull flow without fixed sprints.
  5. TDD (XP) cycle: Write failing test (Red) → Pass (Green) → Refactor.
  6. Blue-Green = 2 identical prod environments (instant flip/rollback); Canary = gradual % traffic shift.
  7. SAST = static white-box code scan; DAST = dynamic black-box runtime scan.
  8. Basic COCOMO: E = a(KLOC)^b; modes = Organic (2.4, 1.05), Semi-Detached (3.0, 1.12), Embedded (3.6, 1.20).
  9. Function Point (FP) estimation is programming-language independent (VAF = 0.65 + 0.01ΣF_i).
  10. PERT: T_e = (O + 4M + P)/6; σ = (P - O)/6.
  11. Critical Path (CPM) = LONGEST path through project network with Zero Slack/Float.
  12. Verification = "Building product RIGHT?" (static); Validation = "Building RIGHT product?" (dynamic).
  13. McCabe Cyclomatic Complexity: V(G) = E - N + 2 = P + 1 = R (min basis paths).
  14. White-box coverage strength: Statement < Branch < Condition < Path.
  15. BVA test cases for n inputs: 4n + 1 (normal), 6n + 1 (robust).
  16. Top-Down Integration uses Stubs; Bottom-Up Integration uses Drivers.
  17. Alpha Testing = developer's site; Beta Testing = customer's live environment.
  18. Regression Testing verifies code changes didn't break existing working features.
  19. Smoke Test = wide shallow build verification; Sanity Test = narrow deep post-bugfix check.
  20. Perfective Maintenance (new features/enhancements) accounts for the LARGEST (~50%+) maintenance cost!
  21. Adaptive Maintenance updates software for new OS, hardware, or regulatory changes.
  22. Preventive Maintenance = refactoring/re-engineering to reduce future defects.
  23. CMMI 5 Levels: Initial → Managed → Defined → Quantitatively Managed → Optimizing.
  24. Availability = MTTF / (MTTF + MTTR); MTBF = MTTF + MTTR.
  25. Banking SDLC enforces Segregation of Duties (SoD) + CAB sign-off before production deployment.
